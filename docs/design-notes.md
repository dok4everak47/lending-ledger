# 设计笔记

这份文档记录几个「本来可以另一个写法」的决定，以及为什么没选那个写法。代码在 `src/` 里能看出**做了什么**，这里回答**为什么**。

招聘方和评审者通常只问三类问题：边界怎么划的、错了怎么办、为什么不用现成的。下面按这三类组织。

---

## 一、金额为什么不用 Decimal 库

**选择**：全部用 `number` 存最小货币单位（分）的整数，配 `Number.isSafeInteger` 校验。

**替代方案**：`decimal.js` / `big.js` / `bignumber.js`。

**理由**：

1. **误差来源不同**。浮点用在账务上出事，不是因为「浮点不准」，而是因为**把金额当成了连续量**。一旦单位固定为分，加减乘除里的加、减、比大小全是精确整数运算，`decimal.js` 在这里不提供额外正确性，只提供额外的对象分配和类型噪音。
2. **数据库是整数**。SQLite 的 `INTEGER` 是 64 位，`SUM()` 精确；换成 `DECIMAL`/字符串存储，反而要在应用层和 SQL 层做两次转换，每次转换都是一个可能引入误差的地方。
3. **序列化安全**。整数在 JSON、日志、HTTP 里往返不会变。`Decimal` 要序列化成字符串，还要约定格式，多一层约定就多一层不一致。

**真正的代价**（诚实记录）：

- 除法必须自己写。`multiplyByRate(money, 6, 1000)` 收整数分子分母，内部先乘后四舍五入，避免 `minor * 0.006` 直接把浮点误差带进来。
- 超过 2^53 分（约 90 万亿元）会溢出。做借贷业务够用，做国债清算不够用——那种场景要用 `BigInt` 或数据库的 `NUMERIC`。

**什么时候该换**：需要多位小数（利率、汇率中间价、加密货币的 8 位小数）时，整数分会变得别扭，那时候 `decimal.js` 或定点数（scaled integer + 明确的 scale）才对。本仓库的 `Currency` 只是占位，没有汇率表，所以不假装支持。

## 二、并发为什么交给数据库，而不是应用层加锁

**选择**：`BEGIN IMMEDIATE` + `busy_timeout`，靠 SQLite 的写锁串行化事务。

**替代方案**：Node 单线程的天然串行（真的吗）、内存里的 mutex、Redis 分布式锁、乐观锁版本号。

**理由**：

1. **单线程不等于事务安全**。`await` 一出现，两个请求就能在同一段业务逻辑里交错。Node 的「单线程」只保证不并行执行 JS，不保证 `读余额 → 判断 → 写分录` 这三步之间没人插队。
2. **进程内 mutex 在多实例部署下等于没有**。你加了三台机器，锁就退化成「每台机器各自为政」。这个 bug 在压测时不会出现，在上线第二台机器时出现。
3. **`BEGIN IMMEDIATE` 一上来就拿写锁**。SQLite 默认的 `DEFERRED` 是「先读后写、写时才升级锁」，升级失败时事务已经做了一半，错误更晚、更难定位。直接拿写锁，冲突发生在最开头，语义最干净。
4. **`busy_timeout` 让等待而不是失败**。跨进程实测（`test/concurrency.test.ts`，6 个进程抢同一把幂等键），第二个进程会阻塞约 1 秒后拿到锁，而不是立刻报 `SQLITE_BUSY`。

**跨进程验证**：这是唯一我肯相信的证据。6 个真进程、真文件库、同一把幂等键，断言只有一个进程扣款、其余全是重放、账簿只多一笔分录、并发后依然借贷平衡。

**真正的代价**：

- 写事务是全库串行的。热点账户（比如平台手续费收入）会成为瓶颈，本仓库没有处理。
- SQLite 单写者模型，不适合多实例高并发写入。生产该换 PostgreSQL 的 `SERIALIZABLE` 或行级锁 + 幂等表。

## 三、幂等为什么用「先插入再判断」，而不是「先查再写」

**选择**：`INSERT` 幂等键，成功者获得执行权；失败者按 `fingerprint` 判断是重放还是冲突。

**替代方案**：`SELECT ... WHERE key = ?` 有就返回、没有就执行并写入。

**理由**：**先查再写在并发下必然漏**。两个请求同时查，都发现「没有」，都去执行，两笔都扣款。这个漏洞在单线程测试里永远测不出来，因为测试是顺序的。

具体语义：

| 场景 | 行为 |
|---|---|
| 同 key 同参数 | 返回首次响应，`replayed: true` |
| 同 key 异参数 | 409，绝不静默执行 |
| 同 key 处理中（`IN_PROGRESS`） | 409，让客户端退避重试 |
| 业务执行抛错 | 幂等键随事务一起回滚，重试会真的重跑 |

最后一条是刻意的：如果失败也留键，那么一次网络抖动就能让这笔单永久卡死（客户端永远拿到"正在处理"），只能人工介入。宁可重试重跑，也不留脏键。

**代价**：`response` 字段要把整个响应体序列化存下来，大响应体会让幂等表膨胀。生产要配 TTL 归档。

## 四、判重为什么用「部分唯一索引」，而不是应用层判断

```sql
CREATE UNIQUE INDEX idx_entries_reversal_unique
  ON journal_entries (reversal_of)
  WHERE reversal_of IS NOT NULL;
```

**理由**：应用层的「先查有没有冲正过，没有就冲」在并发下同样会漏。把不变量下沉到表结构，应用层的判断就退化成「为了给用户一个好错误信息」，而不是「正确性的唯一保障」。

这个思路贯穿全库：`CHECK (amount > 0)`、`CHECK (side IN ('DEBIT','CREDIT'))`、`UNIQUE (entry_id, seq)`、`CHECK (status IN (...))`。**能写成约束的，绝不写成 if。**

**代价**：约束报错信息难看（`SQLITE_CONSTRAINT_UNIQUE`），所以每层都要把数据库错误翻译成领域错误，否则用户看到的就是一串英文。

## 五、冲正为什么不改原分录

**选择**：新增一笔方向相反的等价分录，`reversal_of` 指向原分录。

**替代方案**：`UPDATE postings SET amount = 0`、`DELETE` 掉错的那笔。

**理由**：

1. **审计要求**。账务系统必须能回答「三天前这笔为什么是 100 块」。改了原分录，这个问题就永远没有答案。
2. **对账依赖历史**。银行回单对的是当时的账，不是改完之后的账。删了原分录，对账差异会凭空出现。
3. **可追溯的因果链**。冲正分录带着 `reversal_of`，从任意一笔账都能还原「谁冲了谁、为什么冲」（`transfer_status_events` 里有 reason）。

**代价**：账越冲越长，读余额要扫全部分录。生产要做「期末余额 + 区间流水」的增量计算，本仓库偷懒用了全量 `SUM()`。

## 六、对账为什么必须分类，而不是报一个差异总数

**理由**：总数没有行动含义。"差异 5 元" 这句话，运营看完不知道该干什么。分类之后：

| 类型 | 处置动作 | 谁来做 |
|---|---|---|
| `MISSING_IN_BANK` + 在途窗口内 | 等，次日重跑 | 系统 |
| `MISSING_IN_BANK` + 超窗 | 向渠道追单 | 运营 |
| `MISSING_IN_LEDGER` | 按回单补记 + 查丢单 | 财务 + 研发 |
| `AMOUNT_MISMATCH` | 查手续费/退款/汇率 | 财务 |
| `DUPLICATE_IN_BANK` | 找渠道核实 | 运营 |
| `DUPLICATE_IN_LEDGER` | 冲正多余那笔 | 研发 |

**「总量轧平」是陷阱**：一笔多记 100、一笔少记 100，净差为 0，但两笔都错。所以 `reconciled` 的定义是「无差异 **且** 净差为 0」，少一个都不算平。这条在 `test/recon.test.ts` 里专门钉了一个用例。

## 七、状态机为什么单独抽出来

**理由**：状态迁移是最容易在 service 里散成一堆 `if` 的东西。散开之后，`POSTED → AUTHORIZED` 这种倒退可能出现在任何一个分支里，而没人能一眼看出全部合法路径。

抽成一张显式的表（`ALLOWED`），好处是：

- 非法迁移抛统一错误，带 `from → to`，日志里直接能定位。
- 新加状态时，编译器会强制你补全迁移表（`Record<TransferStatus, ...>` 是穷尽的）。
- 迁移留痕（`transfer_status_events`）能回答「谁在什么时候把它推到这一步」。

## 八、明确没做的，以及为什么不做

| 没做 | 为什么 | 真做要什么 |
|---|---|---|
| outbox 模式 | 演示里没有下游消费者，加了就是空转 | 事务性发件箱 + 至少一次投递 + 消费幂等 |
| 哈希链防篡改 | `fingerprint` 只能做内容比对，冒充不了链式锚定 | 前后分录串联哈希 + 定期外部锚定 |
| 多币种与汇率 | `Currency` 只是类型占位 | 汇率表 + 折算时点 + 汇兑损益科目 |
| 鉴权与审计日志 | HTTP 层没有身份概念 | OAuth/JWT + 操作主体落到每条分录 |
| 分库分表 | 单库 SQLite 教会你的东西已经够多 | 一致性哈希 + 跨分片事务 |

写清楚「没做什么」，比含糊地说「这是一个完整实现」更省时间——面试官省下试探的时间，你也省下被追问到崩的时间。

---

## 一句话总结

这个仓库的核心不是「记账代码」，是**三个把正确性从人身上挪走的动作**：

1. 金额从浮点挪到整数分；
2. 不变量从 if 挪到数据库约束；
3. 并发从应用层锁挪到数据库事务。

剩下的都是这三件事的直接后果。
